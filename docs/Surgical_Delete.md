# Подсистема хирургического удаления

**Subsystem:** Finance Core / Cashier Admin  
**Status:** Development  
**Version:** 0.1  
**Primary module:** `tools/cashier_admin/cashier_admin_ui.py`  
**Primary database:** `Data/db/osbb_test.db`

---

## Назначение

Подсистема хирургического удаления предназначена для контролируемого удаления ошибочно созданной финансовой бизнес-операции вместе со всем связанным с ней информационным шлейфом.

> В OSBB удаляется не запись базы данных, а ошибочно созданная бизнес-операция.

Результатом удаления должно быть согласованное состояние базы данных без осиротевших ссылок и частично удалённых финансовых документов.

---

## Область ответственности

Подсистема отвечает за:

- поиск ошибочного платежа;
- построение плана удаления всей связанной цепочки;
- отображение состава цепочки до удаления;
- обязательный выбор причины и подтверждение;
- создание резервной копии базы;
- удаление связанных записей в установленном порядке;
- транзакционный rollback при ошибке;
- регистрацию хирургического удаления в отдельном журнале.

Подсистема не предназначена для обычного архивирования, изменения тарифов, переноса средств между услугами или бухгалтерского сторно.

---

## Доступ и точка входа

Точка входа находится в рабочем месте администратора кассы. Раздел `Админ платежей` доступен только суперадминистратору.

Оператор может:

- открыть последние платежи;
- найти платёж по квартире, номеру автомобиля, ФИО, дате, сумме, услуге или номеру чека;
- выбрать один или несколько платежей;
- запустить `Удалить со шлейфом` или `Удалить выбранные`;
- выбрать причину;
- подтвердить операцию.

Коды причин:

- `OPERATOR_ERROR`;
- `TECHNICAL_FAILURE`;
- `SOFTWARE_DEFECT`;
- `DUPLICATE_OPERATION`;
- `TEST_RECORD`;
- `OTHER`.

---

## Главный объект удаления

Корневым объектом является запись `payments`.

По `payment_id` функция `collect_chain()` восстанавливает связанную бизнес-операцию:

```text
payments
├── cashier_receipts
├── cashbox_operations
├── payment_allocations
├── payment_notices
├── resident_payment_notices
├── cashier_reconciliation_cases
├── service_orders
├── service_order_charge_links
├── audit_log
├── operator_audit_log
└── access_audit_log
```

В план включаются только реально найденные записи.

---

## Построение плана удаления

### Один платёж

```python
collect_chain(payment_id: int) -> dict[str, list[int]]
```

Алгоритм:

1. Загружает платёж из `payments`.
2. Через `cashier_receipt_id` находит чек.
3. Определяет кассовую операцию через `payments.cashbox_operation_id` либо `cashier_receipts.cashbox_operation_id`.
4. Определяет связанное уведомление через `payment_notice_id`.
5. Ищет дочерние записи по точным ссылкам.
6. Ищет аудиторские записи по паре «таблица + идентификатор».
7. Возвращает словарь таблиц и идентификаторов.

### Несколько платежей

```python
collect_batch_chain(payment_ids: list[int]) -> dict[str, list[int]]
```

Строит цепочку для каждого платежа и объединяет идентификаторы без повторов.

---

## Защита от ошибочного сопоставления аудита

Числовые `id` повторяются в разных таблицах, поэтому поиск аудита только по идентификатору небезопасен.

`_add_exact_reference()` использует точную пару:

| Журнал | Таблица | Идентификатор |
|---|---|---|
| `audit_log` | `table_name` | `record_id` |
| `operator_audit_log` | `table_name` | `row_id` |
| `access_audit_log` | `target_table` | `target_id` |

---

## Предварительный просмотр

`chain_summary()` показывает оператору количество найденных платежей, чеков, кассовых операций, распределений, уведомлений, заказов, сверок и записей аудита, а также общее число удаляемых строк.

План сохраняется в состоянии интерфейса и применяется только после подтверждения.

---

## Резервное копирование

Перед изменением базы вызывается:

```python
backup_db() -> Path
```

Копия создаётся в:

```text
Data/backups/db/
```

Имя:

```text
before_payment_cleanup_YYYY-MM-DD_HH-MM-SS.db
```

Путь показывается оператору и записывается в журнал удаления.

---

## Порядок удаления

`apply_cleanup_batch()` удаляет записи в явном порядке:

```text
1.  payment_allocations
2.  service_order_charge_links
3.  cashier_reconciliation_cases
4.  payment_notices
5.  resident_payment_notices
6.  service_orders
7.  audit_log
8.  operator_audit_log
9.  access_audit_log
10. cashbox_operations
11. cashier_receipts
12. payments
```

Сначала удаляются зависимые записи, затем финансовые документы, в конце — корневой платёж.

---

## Транзакционность

Все удаления выполняются в одной транзакции.

При успехе — `commit()`. При исключении — `rollback()`.

Это исключает частично выполненное удаление. Дополнительно до начала операции создаётся полная резервная копия базы.

---

## Журнал хирургического удаления

Используется отдельная таблица:

```sql
developer_cleanup_log
```

Она создаётся автоматически функцией `ensure_cleanup_log()`.

| Поле | Назначение |
|---|---|
| `id` | идентификатор записи |
| `performed_at` | время операции |
| `performed_by` | Telegram ID администратора |
| `payment_id` | удалённый платёж |
| `receipt_id` | связанный чек |
| `reason_code` | код причины |
| `reason_text` | текст причины |
| `backup_path` | путь к резервной копии |
| `deleted_summary` | сохранённый план удаления |

При пакетном удалении создаётся запись на каждый корневой платёж.

## Инварианты

После успешного удаления:

1. Платёж отсутствует в `payments`.
2. Связанный чек отсутствует в `cashier_receipts`.
3. Связанная кассовая операция отсутствует в `cashbox_operations`.
4. Нет распределений удалённого платежа.
5. Нет уведомлений и сверок, ссылающихся на операцию.
6. Нет связанных заказов и связей заказов.
7. Нет аудиторских записей, относящихся к физически удалённым объектам.
8. В `developer_cleanup_log` сохранён факт удаления.
9. Существует резервная копия состояния до операции.
10. Ошибка не может оставить частично удалённую цепочку.

## Выявленные ограничения

### 1. Удаление исходного аудита

Текущий код удаляет записи `audit_log`, `operator_audit_log` и `access_audit_log`, относящиеся к удаляемым объектам.

История исходной операции после этого сохраняется только в резервной копии и `developer_cleanup_log`. Политику необходимо подтвердить архитектурно.

### 2. Пересчёт кассы

В найденном коде нет явного пересчёта:

- `cashboxes.current_balance`;
- агрегированных кассовых итогов;
- статусов начислений после удаления распределений.

Это требует отдельной проверки.

### 3. Полнота цепочки

Список зависимостей задан вручную. Новая таблица, ссылающаяся на платёж, автоматически в цепочку не попадёт.

### 4. Пакетное соответствие платёж ↔ чек

При журналировании пакетного удаления чек выбирается позиционно из общего списка `receipt_ids`. Для сложных случаев соответствие не гарантировано.

### 5. Архитектурное размещение

Бизнес-алгоритм находится внутри UI-модуля. Целевое направление:

```text
Presentation Layer
    ↓
Finance Core service
    ↓
Data Access
```

## Связанные принципы

- Пользователь работает с бизнес-операцией, а не с таблицами.
- Исключительные ситуации являются штатными сценариями.
- История операций является частью ценности OSBB.
- Финансовое изменение должно быть объяснимым и проверяемым.
- Физическое удаление допустимо только как специальная административная операция.
