# Политика разрешений ОСББ: восстановление 2026-09-26

## Редактор в каталоге

В боте: «Каталог услуг» → «Изменить существующую услугу» → позиция →
«Условия заказа». Просмотр доступен менеджеру каталога, запись — только
активному SUPER_ADMIN. В админ-консоли: выбрать строку каталога → раскрыть
«Условия заказа — политика задолженности». До персонального входа консоль
использует явно обозначенный локальный однопользовательский режим;
исполнитель в аудите — `local_mac:<имя пользователя>`.
Указываются режим, область задолженности, сообщение и обязательное
основание. Перед записью показываются все позиции затрагиваемой категории.
Общее ядро — `get_access_policy` / `save_access_policy` в
`service_catalog_admin_core.py`. Созданный черновик настраивается через ту
же карточку перед публикацией; отдельного дублирующего редактора нет.
Изменение не переписывает историю уже созданных заказов.

Это бизнес-политика услуг, не роли RBAC. Исходный проект от 2026-06-29:
`business_policy_layer_v1_design.md`. Рабочий движок сохранился в
`service_access_policy.py`; предварительная матрица —
`tools/debt_policy_matrix_preview.py`, миграции —
`tools/MIGRATE_debt_policy_rules_v1.py` и
`tools/MIGRATE_service_catalog_v2_policy_fields.py`.

## Действующие правила в БД

| Категория | Область долга | Режим |
|---|---|---|
| BARRIER_PHONE, BARRIER_PHONE_CONNECT | PARKING | BLOCK |
| TEST_PHONE_ACCESS_CONNECT (тестовая) | PARKING | BLOCK |
| REMOTE | NONE | политика выключена |
| Остальные категории в текущем каталоге | NONE | политика выключена |

Это снимок настроек, а не новые решения правления. Режим WARN поддерживается
кодом, но в проверенном каталоге сейчас не назначен ни одной категории.
Не следует самовольно включать блокировку пультов или других услуг.

## Как принимается решение

Поля `service_catalog.access_policy_enabled`, `access_policy_scope`,
`access_policy_mode`, `access_policy_message`, `manual_review_required`
описывают правило. Позиция `service_items` ссылается на категорию.
Долг считается как начисления `charges` минус распределения
`payment_allocations`; нераспределённая оплата сама по себе не погашает
конкретное начисление. Поэтому BLOCK требует сверки, а не обвинения жителя.

| Решение | Последствие |
|---|---|
| ALLOW | заказ можно создать |
| WARN | заказ разрешён, результат содержит предупреждение |
| BLOCK | заказ не создаётся до оплаты/сверки |
| ERROR | заказ не создаётся: ошибка определения услуги |

Намерения принимаются всегда. 2026-09-26 проверка восстановлена в общем
`service_orders_core.create_service_order`, так что операторский вход,
бот и преобразование оплаченного намерения не обходят её. Решение и сумма
долга фиксируются в событии ORDER_CREATED, результат возвращает
`access_policy`. Настройки БД при восстановлении не менялись.

## Что ещё не является готовой системой политик

Предупреждение WARN возвращается ядром, но это не гарантирует отдельный
экран напоминаний во всех интерфейсах. Повторная проверка непосредственно
перед выдачей/активацией и админский редактор общей матрицы требуют следующего
этапа. `manual_review_required` пока не является самостоятельной очередью
согласования. Нельзя путать архитектурные планы с реализованными проверками.
При BLOCK кассовое подтверждение, выполняемое совместно с созданием заказа,
может откатиться транзакцией: отдельный учёт уже фактически принятых денег
при заблокированном заказе нужно проектировать явно, без потери денег
и без фиктивного оплаченного заказа.
