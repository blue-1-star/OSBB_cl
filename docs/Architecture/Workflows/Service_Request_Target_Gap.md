# Цель развития подсистемы заказов услуг и уведомлений

**Subsystem:** Service Request & Notification Workflow  
**Status:** target gap  
**Version:** 0.1

## 1. Формула цели

```text
целевая модель
−
реализованная часть
=
направление развития
```

Нужно не создавать подсистему с нуля, а соединить уже существующие сильные части в один объяснимый поток.

## 2. Главный разрыв

Не подтверждён единый маршрут:

```text
выбор услуги
→ проверка политики
→ решение
→ заказ или отказ
→ уведомление
→ адресаты
→ доставка
→ исполнение
→ завершение
→ аудит
```

## 3. Единая точка входа

Нужен один прикладной сервис заказа услуги.

Он должен:

1. определить жителя и квартиру;
2. загрузить `service_item`;
3. определить workflow profile;
4. получить действующую цену;
5. вызвать Policy Engine;
6. сохранить решение;
7. создать interest или order;
8. создать шаги;
9. создать финансовые связи;
10. породить уведомления;
11. вернуть объяснимый результат.

Telegram и операторский интерфейс должны вызывать один и тот же сервис.

## 4. Policy Engine

Вход:

- житель;
- квартира;
- вариант услуги;
- долг;
- ранее выданные пульты;
- состояние доступа;
- действующая версия политики;
- контекст обращения.

Результат:

```text
ALLOW
ALLOW_WITH_WARNING
DENY
```

Дополнительно:

- `reason_code`;
- понятный текст;
- версия политики;
- снимок проверенных данных;
- требуемые дальнейшие действия.

### Новый пульт

```text
долг за парковку
→ DENY
→ заказ отклонён
→ жителю и оператору отправлена причина
```

### Перепрошивка старого пульта

```text
долг за парковку
→ ALLOW_WITH_WARNING
→ заказ принят
→ предупреждение сохранено и отправлено
```

## 5. История решения политики

Нужно сохранять для каждого решения:

- order или interest;
- service item;
- результат;
- reason code;
- policy version;
- входной snapshot;
- текст предупреждения;
- источник;
- время.

Это можно оформить отдельной таблицей `service_policy_decisions` либо строгим типом `service_order_events`.

## 6. Единый Notification Engine

Существующие специализированные таблицы должны остаться предметными документами, но доставка должна стать общей.

Целевая схема:

```text
business event
→ notifications
→ notification_recipients
→ notification_deliveries
→ Telegram / email / internal task
```

`notifications` хранит смысл сообщения.

`notification_recipients` хранит адресатов.

`notification_deliveries` хранит канал, попытки, статус и ошибку.

## 7. Правила адресатов

Адресаты должны определяться декларативно:

```text
SERVICE_ORDER_DENIED
→ заявитель
→ оператор очереди
```

```text
REMOTE_ORDER_PAID
→ заявитель
→ ответственный за пульты
```

```text
PHONE_ACCESS_DEBT_WARNING
→ житель
→ оператор доступа
```

## 8. Соединение специализированных потоков

### Пульты

Закрепить:

```text
service_order_id
→ remote_order_details
→ physical asset lifecycle
```

### Телефонный доступ

Выбрать канонический путь между:

- `phone_access_*`;
- `phone_barrier_access_*`;
- `barrier_phone_access`;
- `access_*`.

Старые таблицы могут остаться для миграции, но новая операция должна идти по одному маршруту.

## 10. Целевая архитектура

```text
Presentation Layer
    ↓
Service Request Application Service
    ↓
Policy Engine + Workflow Engine
    ↓
Remote / Phone Access domain services
    ↓
Repositories / Core_New
    ↓
Database
```

UI не должен сам проверять долг, выбирать политику или создавать набор связанных записей.

## 11. Тесты приёмки

1. Новый пульт без долга — заказ принят.
2. Новый пульт с долгом — отказ с причиной.
3. Перепрошивка с долгом — заказ принят с предупреждением.
4. Телефонный доступ — создаются выбранные точки.
5. Платная услуга — заказ связан с начислением и платежом.
6. Завершение шага — событие в истории.
7. Смена политики не меняет объяснение старого решения.
8. Ошибка доставки остаётся в очереди повторной отправки.
9. Несколько адресатов получают независимые доставки.
10. Отказ в услуге также сохраняется как полноценная бизнес-операция.

## 12. Приоритет движения

### P0

Найти точные Python-модули и функции текущего контура.

### P1

Связать `service_item` с формальным Policy Engine.

### P2

Создать одну точку заказа для всех интерфейсов.

### P3

Создать общий Notification Engine поверх существующих специализированных документов.

### P4

Перевести пульты и телефонный доступ на канонический pipeline без потери их предметных данных.

## 13. Образ результата

Система должна отвечать:

- кто заказал;
- какую услугу;
- какая политика применена;
- почему разрешено, разрешено с предупреждением или отказано;
- сколько стоит;
- как оплачено;
- какие шаги выполнены;
- кто отвечает;
- кому отправлено уведомление;
- доставлено ли оно;
- чем и когда завершён заказ.
