# Намерения, запросы услуг и уведомления о передаче денег

**Subsystem:** Service Request & Cash Handover Notice Workflow  
**Status:** фактическое состояние + целевое встраивание  
**Version:** 0.1  
**Recommended location:** `Docs/Architecture/Business_Workflows/Service_Interest_and_Payment_Notice_Workflow.md`

---

## 1. Назначение

Документ разделяет три разных бизнес-факта:

1. намерение получить услугу;
2. оформленный запрос или заказ услуги;
3. уведомление жителя о том, что деньги уже переданы либо перечислены.

Эти события похожи только тем, что исходят от жителя. По смыслу и последствиям они различны и не должны храниться как один объект.

---

## 2. Три разных события

### 2.1. Намерение получить услугу

Пример:

```text
«Хочу заказать новый пульт»
```

Это ещё не выполненная услуга и не подтверждённая оплата.

Фактически в проекте для этого используются структуры:

- `service_order_interests`;
- `service_interests`;
- `phone_barrier_access_interests`;
- `phone_barrier_access_interest_points`.

Общий смысл:

```text
интерес жителя
→ выбранная услуга
→ выбранные параметры
→ возможная проверка и ожидание оплаты
→ создание заказа
```

### 2.2. Запрос или заказ услуги

Пример:

```text
«Заказ на новый пульт принят в работу»
```

Подтверждённые структуры:

- `service_orders`;
- `service_order_steps`;
- `service_order_events`;
- `service_order_payment_links`;
- `service_order_charge_links`.

Специализированные запросы:

- `remote_requests`;
- `phone_access_requests`;
- `phone_access_request_points`.

### 2.3. Уведомление о передаче денег

Пример:

```text
«500 грн переданы в К1 за новый пульт»
```

Это не намерение заплатить. Житель заявляет, что физическое или банковское действие уже произошло.

До подтверждения принимающей стороной это ещё не бухгалтерский платёж, но уже зарегистрированное свидетельство жителя.

Для этого фактически реализована таблица:

- `payment_notices`.

## 3. Фактический поток намерения и заказа услуги

### 3.1. Общий поток

```text
service_catalog
→ service_items
→ service_item_workflows
→ service_workflow_profiles
→ service_workflow_steps
→ service_order_interests
→ service_orders
→ service_order_steps
→ service_order_events
```

`service_order_interests` хранит, среди прочего:

- жителя и Telegram-пользователя;
- квартиру;
- услугу и вариант услуги;
- снимок названия;
- профиль workflow;
- количество;
- снимок цены и суммы;
- статус;
- `payment_notice_id`;
- `payment_notice_number`;
- `payment_id`;
- ссылку на созданный заказ;
- комментарий жителя.

Это показывает, что в модели уже предусмотрена связь:

```text
интерес к услуге
→ уведомление об оплате
→ платёж
→ заказ
```

Точная функция перехода `interest → order` в доступном наборе кода не найдена.

## 4. Специализированные потоки услуг

### 4.1. Пульт

Фактически существуют:

- `remote_requests`;
- `remote_order_details`;
- `remote_order_issued_assets`;
- `remote_assets`;
- `remote_asset_movements`;
- `remote_handover_events`;
- `remote_supplier_batches`;
- `remote_supplier_batch_links`.

Поток:

```text
интерес или запрос жителя
→ service_order
→ remote_order_details
→ резервирование или выдача актива
→ движение пульта
→ событие передачи
```

`remote_requests` уже имеет `service_order_id`, то есть старая или специализированная заявка может быть связана с общим заказом.

### 4.2. Телефонный доступ

Фактически существуют:

- `phone_access_requests`;
- `phone_access_request_points`;
- `phone_access_subscriptions`;
- `phone_access_subscription_points`;
- `phone_access_subscription_charges`.

`phone_access_requests` содержит:

- `interest_id`;
- `service_order_id`.

Это подтверждает явную цепочку:

```text
interest
→ phone access request
→ service order
→ subscription
```

Также существует более новая группа:

- `phone_barrier_access_interests`;
- `phone_barrier_access_interest_points`;
- `phone_barrier_access_order_points`.

Она подтверждает, что отдельная стадия интереса к телефонному доступу была заложена архитектурно.

## 5. Фактический поток уведомления о передаче денег

### 5.1. Таблица `payment_notices`

Таблица хранит:

- номер уведомления;
- тип;
- статус;
- жителя и Telegram-пользователя;
- квартиру;
- заявленную точку приёма;
- период;
- услугу и вариант услуги;
- заявленную сумму;
- дату заявления;
- комментарий и текст свидетельства;
- связанный кассовый чек;
- связанную банковскую операцию;
- связанный платёж;
- оператора;
- время рассмотрения, подтверждения или отклонения.

Поддержаны типы:

```text
CASH_HANDOVER
BANK_TRANSFER
```

Для наличных код проверяет точки:

```text
O
K1–K6
C
```

### 5.2. Создание уведомления

В модуле:

```text
tools/cashier_v2_telegram/cashier_v2_core.py
```

реализована функция:

```python
create_payment_notice(...)
```

Она:

1. проверяет тип уведомления;
2. проверяет допустимую точку приёма наличных;
3. защищает от повторного идентичного уведомления в тот же день;
4. создаёт запись `payment_notices` со статусом `NEW`;
5. присваивает номер;
6. пишет аудит.

Аудиторский комментарий прямо фиксирует смысл:

```text
Житель сообщил о передаче денег.
```

### 5.3. Подтверждение оператором

В том же модуле реализовано подтверждение уведомления.

При подтверждении:

```text
payment_notices.NEW
→ создание cashier_receipt
→ создание payments
→ связывание matched_cashier_receipt_id
→ связывание matched_payment_id
→ payment_notices.CONFIRMED
```

Сохраняются:

- оператор;
- время проверки;
- время подтверждения;
- кассовый чек;
- платёж.

В аудит записывается:

```text
Оператор подтвердил фактическое получение наличных по уведомлению жителя.
```

### 5.4. Отклонение

Реализована функция:

```python
reject_notice(...)
```

Она переводит:

```text
NEW
→ REJECTED
```

и сохраняет:

- оператора;
- причину;
- время рассмотрения;
- время отклонения;
- аудит.

## 6. Важное различие статусов

### Намерение услуги

```text
Житель хочет получить услугу.
```

Финансового события ещё нет.

### Уведомление о передаче

```text
Житель утверждает, что деньги уже переданы.
```

Деньги ещё не подтверждены кассой.

### Подтверждение

```text
Принимающая сторона подтверждает получение.
```

После этого создаются кассовый и платёжный документы.

### Бухгалтерский факт

```text
cashier_receipt
+ payments
+ cashbox_operation
```

Только этот уровень должен менять фактическую кассу и баланс оплаты.

## 7. Как встроить уведомление о передаче денег в заказ услуги

### 7.1. Рекомендуемый поток

```text
service_order_interest
→ policy check
→ service order
→ payment required?
   ├─ нет → выполнение услуги
   └─ да
      → житель передаёт деньги
      → payment_notice.NEW
      → уведомление направляется ответственной точке
      → получатель подтверждает
      → cashier_receipt + payment
      → service_order_payment_links
      → order.payment_status = PAID
      → следующий шаг workflow
```

### 7.2. Главное правило связи

`payment_notice` не должен становиться частью `service_order` как самостоятельный платёж.

Правильная последовательность:

```text
service_order
→ ожидает оплату
→ payment_notice
→ подтверждение
→ payment
→ service_order_payment_links
```

То есть:

- `payment_notice` — заявление жителя;
- `payment` — подтверждённый финансовый факт;
- `service_order_payment_links` — связь подтверждённого платежа с заказом.

### 7.3. Связь до подтверждения

Для удобства необходимо иметь прямую ссылку:

```text
payment_notices.service_order_id
```

либо отдельную таблицу:

```text
service_order_notice_links
```

Предпочтительнее отдельная связь, если одно уведомление может покрывать несколько заказов или один заказ может оплачиваться несколькими передачами.

Минимальная таблица:

```text
service_order_payment_notice_links
- id
- service_order_id
- payment_notice_id
- declared_amount
- link_status
- created_at
```

После подтверждения система создаёт обычную запись в `service_order_payment_links`.

## 8. Точки приёма денег и адресаты

Существующая модель уже хранит `declared_cashbox_code`.

Для реального процесса этого недостаточно: код точки должен быть связан с ответственным получателем.

Целевая связь:

```text
collection_points
- point_code       O, K1, K2, ..., C
- point_name
- point_type       GUARD, CONCIERGE, COLLECTOR
- responsible_principal_id
- confirmation_timeout
- escalation_principal_id
- is_active
```

После создания `payment_notice.NEW` адресатом становится ответственный за заявленную точку.

Пример:

```text
declared_cashbox_code = K1
→ ответственный консьерж первого подъезда
```

## 9. Напоминания и эскалация

В найденном коде подтверждены создание, подтверждение и отклонение уведомления.

Автоматический механизм напоминаний по неподтверждённому уведомлению в доступных файлах не найден.

Его следует встроить как отдельный шаг:

```text
payment_notice.NEW
→ истёк confirmation_timeout
→ reminder
→ ответственному получателю
→ при повторной просрочке escalation
```

Текст напоминания:

```text
Согласно уведомлению жителя квартиры 35 от 27.07.2026,
вам передано 500 грн за услугу «Новый пульт».
Подтвердите получение или отклоните уведомление с причиной.
```

Для контроля доставки желательно добавить:

```text
payment_notice_delivery_events
```

Поля:

- `payment_notice_id`;
- `recipient_id`;
- `event_type`;
- `channel`;
- `sent_at`;
- `delivery_status`;
- `external_message_id`;
- `error_text`.

## 10. Политики доступа и оплата

Политика допуска к услуге и подтверждение передачи денег — разные проверки.

Правильная последовательность зависит от услуги.

### Новый пульт

```text
interest
→ проверка долга
→ DENY
```

Если отказано до заказа, уведомление о передаче денег для этого заказа создаваться не должно.

Если деньги уже были переданы ошибочно, создаётся отдельный reconciliation case.

### Перепрошивка старого пульта

```text
interest
→ ALLOW_WITH_WARNING
→ order
→ payment_notice
→ подтверждение
→ выполнение
```

### Телефонный доступ

```text
interest
→ policy check
→ order
→ payment notice or bank notice
→ confirmed payment
→ subscription activation
```

## 12. Инварианты

1. Намерение услуги не является платежом.
2. `payment_notice.NEW` не изменяет баланс кассы.
3. Только подтверждение создаёт `cashier_receipt` и `payment`.
4. Отказ должен сохранять уведомление и причину.
5. Подтверждённое уведомление должно иметь ссылку на созданный платёж.
6. Платёж связывается с заказом через `service_order_payment_links`.
7. Повторное идентичное уведомление в тот же день не должно создавать дубль.
8. Каждое напоминание и подтверждение должно журналироваться.
9. Нельзя активировать оплачиваемую услугу только на основании заявления жителя.
10. При расхождении создаётся `cashier_reconciliation_cases`.

## 13. Цель развития

Фактически уже реализовано ядро:

```text
житель сообщил
→ payment_notices.NEW
→ оператор подтвердил
→ receipt + payment
→ audit
```

Не хватает соединения с общим service workflow:

```text
service interest
→ service order
→ payment notice
→ responsible recipient
→ reminder
→ confirmation
→ payment link
→ next workflow step
```

Это и является ближайшей целью развития подсистемы.
