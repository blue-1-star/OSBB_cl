# Реестр устаревших сущностей и безопасной очистки

Этот документ — не список для немедленного удаления. Он фиксирует сущности,
которые перестали быть источником истины, и условия, при которых их можно
безопасно вывести из эксплуатации.

## `resident_access_accounts` — кандидат на вывод из эксплуатации

**Статус:** legacy, не использовать для новых назначений жителям.

### Почему

Таблица относится к раннему модулю `Пользователи и роли`. Она хранит простую
роль (`resident`, `guard`, `cashier`, `operator`) без точной области доступа и
не является источником истины для нового кабинета жителя.

Для жителей источником истины теперь являются:

| Назначение | Актуальная сущность |
|---|---|
| Telegram-профиль и подтверждённая квартира | `resident_accounts` |
| Права доступа с областью квартиры | `access_user_roles` |
| Правила роли | `access_role_permissions` |
| Аудит выдачи/отзыва доступа | `access_audit_log` |

Для обычного жителя применяется только
`RESIDENT_SELF_SERVICE` с областью `APARTMENT / номер_квартиры`.

### Что в ней осталось на 20.09.2026

Две активные старые записи с ролью `guard`. Жителей в таблице нет.
Следовательно, таблицу нельзя удалить прямо сейчас: это затронет старый экран
охранников, даже если его данные уже требуют переноса в ACL.

### Условия удаления

1. Провести инвентаризацию всех обращений к таблице в коде.
2. Для каждой активной записи перенести нужную роль в `access_user_roles` с
   корректной областью доступа и проверить вход соответствующего сотрудника.
3. Перевести экран «Пользователи и роли» на `resident_accounts` +
   `access_user_roles`; старую таблицу оставить только на чтение на один
   тестовый цикл.
4. Создать резервную копию БД и отчёт миграции с перечнем перенесённых записей.
5. После подтверждения оператором — удалить таблицу отдельной обратимой
   миграцией либо сначала переименовать её в `resident_access_accounts_legacy`.

До выполнения этих условий не добавлять в неё новых жителей, роли или
привязки квартир.
