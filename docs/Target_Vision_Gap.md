# Целевое состояние OSBB — разница между замыслом и реализацией

**Статус:** стратегическая цель 0.1

```text
Техническое задание
−
Фактическое состояние
=
Цель развития OSBB
```

## Главная цель

Создать единую объяснимую систему, в которой ежедневный цикл ОСББ проходит без ручного восстановления смысла из таблиц, сообщений и памяти оператора.

```text
житель и объект
→ услуга
→ действующий тариф
→ начисление
→ поступление
→ распределение
→ баланс
→ касса/банк
→ уведомление
→ отчёт
→ аудит
→ корректировка
```

## 1. Завершить эксплуатационный контур кассы

**Есть:** Telegram-кассир, создание receipt/payment, выбор услуги, периода и суммы.  
**Нужно:** стабильный компактный UI, состояние кассы после операции, несколько автомобилей, частичная оплата, банковский источник, отделение UI от финансовой логики.  
**Результат:** кассир ежедневно работает без ручного вмешательства разработчика.

## 2. Реализовать первую вертикаль Finance Core

**Есть:** архитектурное решение, payment_allocations, receipts, payments и cashbox operations.  
**Нужно:** реализовать `700 получено → 500 распределено → 200 нераспределено`, затем последующее распределение, аванс, перенос, возврат и корректировку.  
**Результат:** система честно отражает поступление даже при неизвестном назначении части суммы.

## 3. Создать единый тарифный движок

**Есть:** коды услуг, service items, тарифные таблицы и временные значения.  
**Нужно:** один источник цены, интервалы действия, расчёт по истории, удаление констант из UI.  
**Результат:** любой баланс объясним тарифами соответствующих периодов.

## 4. Завершить начисления и баланс

**Есть:** услуги, периоды, платежи и отдельные расчёты.  
**Нужно:** начисление как операция, частичное погашение, задолженность, переплата, аванс, корректировки и единые инварианты.  
**Результат:** один канонический баланс квартиры, автомобиля и услуги.

## 5. Разделить роли

**Есть:** legacy resident flow и решение в Roadmap.  
**Нужно:** Resident Cabinet, Operator Workspace и Super-admin Diagnostic View без скрытой подмены личности.  
**Результат:** всегда понятно, от чьего имени выполнено действие.

## 6. Завершить банковский контур

**Есть:** временная идея «БАНК + reference».  
**Нужно:** источники, импорт выписки, защита от дублей, распознавание, очередь исключений, распределение и сверка.  
**Результат:** банковский и наличный платежи проходят единый финансовый путь.

## 7. Создать единую систему аудита и исправлений

**Есть:** audit-таблицы, cleanup log, Surgical Delete, backup и rollback.  
**Нужно:** единый формат события, политика сторно/корректировки/удаления, проверка целостности, перенос Surgical Delete из UI в доменный сервис.  
**Результат:** любую операцию можно объяснить, проверить и безопасно исправить.

## 8. Построить отчётный слой

**Есть:** query_lib и точечные SQL.  
**Нужно:** утверждённые отчёты по балансам, кассе, банку, должникам, авансам, нераспределённым деньгам, тарифам, аудиту и целостности.  
**Результат:** правление получает ответы из системы без разовых SQL-запросов.

## 9. Довести архитектурное разделение

```text
Telegram / Admin / Reports
            ↓
Application Services
            ↓
Finance Core / Service Domains
            ↓
Core_New
            ↓
Database
```

Нужно убрать произвольный SQL и финансовые правила из UI, создать единые команды записи, тестируемые доменные правила и план миграции legacy.

## 10. Сделать развитие измеримым

**Есть:** Roadmap, Project Log, Chronicle, Daily Handoff, архитектурные документы и Assistant.  
**Нужно:** регулярно обновлять `Implementation_Status.md`, связывать задачи с ТЗ, хранить критерии приёмки и использовать разрыв как источник Roadmap.  
**Результат:** проект движется по видимой карте цели.

## Приоритеты

### P0 — Реальная эксплуатация

- стабилизировать Telegram-кассу;
- принимать реальные платежи;
- обеспечить backup, журнал и восстановление;
- не блокировать эксплуатацию ожиданием идеальной архитектуры.

### P1 — Финансовая достоверность

- Finance Core 700/500/200;
- история тарифов;
- канонический баланс;
- касса и распределения.

### P2 — Разделение ролей и процессов

- Resident Cabinet;
- Operator Workspace;
- Diagnostic View;
- банковская сверка;
- заявки.

### P3 — Управляемость

- отчёты;
- единый аудит;
- тесты инвариантов;
- миграция legacy;
- интеграция с бухгалтерским учётом.

## Образ достигнутой системы

OSBB сама отвечает:

- кто должен;
- за что;
- по какому тарифу;
- за какой период;
- сколько получено;
- как деньги распределены;
- какой остаток;
- где находятся деньги;
- кто и почему изменил данные;
- как безопасно исправить ошибку.
