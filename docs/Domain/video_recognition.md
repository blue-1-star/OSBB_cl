# Видео-распознавание парковки: подготовка и использование данных

## Назначение

Excel-файлы с результатами распознавания видео — самостоятельный, четвёртый
источник сведений об автомобилях наряду с бумажными таблицами, выгрузками
старого бота и сообщениями жителей. Они помогают оператору проверить номер
или модель, но не являются основанием для автоматической правки реестра.

Первичная обработка выполнена 2026-09-19: 32 исходных Excel-файла дали
1 770 наблюдений и 181 уникальный номер, соответствующий стандартному
украинскому шаблону. Исходные файлы не изменялись.

## Где лежат данные

- Исходные Excel-файлы: `Data/raw/video_recognition/`.
- Сформированный рабочий Excel-отчёт: `outputs/2026-09-19-video-recognition/`.
  Это воспроизводимый результат обработки, не первоисточник.
- Операторский кэш в БД: таблица `video_plate_evidence`; история его
  обновлений — `video_recognition_imports`.

Описание полей БД находится в
[Data Dictionary](../Database/Data_Dictionary.md#14-таблица-video_plate_evidence-агрегированное-доказательство-из-видео).

## Конвейер обработки

### 1. Приведение исходных файлов к единому виду

Модуль [`tools/standardize_video_recognition.py`](../../tools/standardize_video_recognition.py)
читает каждый `.xlsx` в `Data/raw/video_recognition/` в режиме только чтение.
Он распознаёт оба встречавшихся варианта заголовков, в том числе:

| Исходный вариант | Единое поле |
|---|---|
| `Car Make/Model`, `Make/Model` | `make_model` |
| `Plate`, `License Plate` | `plate` |
| `Video Date`, дата в имени файла | `video_date` |
| `Video Time`, время в заголовке | `video_time` |
| `Video Part Number`, `Video Part` | `video_part_number` |

Дата и тип съёмки (`DAY`/`NIGHT`) извлекаются из имени файла. Номер очищается
от пробелов, дефисов и похожих кириллических букв; результат хранится вместе с
исходным написанием. Номер, который после этого не соответствует шаблону
`AA1234AA`, помечается `CHECK`, а не исправляется догадкой. Для каждой строки
сохраняются имя файла, лист и номер исходной строки — это позволяет вернуться
к первоисточнику.

Пример диагностического, не изменяющего БД запуска:

```zsh
.venv/bin/python tools/standardize_video_recognition.py \
  --output /tmp/video_recognition_standardized.json
```

### 2. Рабочая книга для визуальной проверки

[`tools/build_video_recognition_workbook.mjs`](../../tools/build_video_recognition_workbook.mjs)
строит Excel-файл с листами `Review`, `Observations` и `Sources`.
В `Sources` видны фактически найденные заголовки, количество принятых и
пропущенных строк. Скрипт предназначен для подготовки отчёта и использует
проектный runtime для работы с Excel; он не меняет БД и не требуется для
обычного обновления подсказок оператору.

[`tools/enrich_video_recognition_models.mjs`](../../tools/enrich_video_recognition_models.mjs)
добавляет в эту рабочую книгу свод по модели для каждого номера. Модель
предлагается только если она побеждает без ничьей:

- `CONSENSUS` — не менее двух наблюдений и не менее 75 % среди наблюдений,
  где модель распознана;
- `DOMINANT — REVIEW` — лидер есть, но согласие ниже 75 %;
- `CONFLICT`, `ONE OBSERVATION`, `NO MODEL` — модель не предлагается как
  надёжная.

Пустая модель в отдельной строке означает не отсутствие автомобиля, а то, что
распознавание не смогло определить марку/модель именно в этом наблюдении.

### 3. Обновление подсказок в БД

Основной рабочий модуль —
[`tools/import_video_recognition_evidence.py`](../../tools/import_video_recognition_evidence.py).
Он повторно читает исходные файлы через стандартизатор, агрегирует наблюдения
по нормализованному номеру и обновляет кэш в одной транзакции. Перед записью
можно выполнить безопасный dry-run:

```zsh
.venv/bin/python tools/import_video_recognition_evidence.py
```

Обновление кэша выполняется явно:

```zsh
.venv/bin/python tools/import_video_recognition_evidence.py --apply
```

При `--apply` скрипт фиксирует подпись набора файлов, число источников,
наблюдений и номеров в `video_recognition_imports` и создаёт запись в
`audit_log`. Реестр `vehicles` он не изменяет: даже точное совпадение номера
и согласованная модель остаются подсказкой, которую оператор применяет
отдельным подтверждённым действием.

## Отчёты наблюдений

[`tools/build_video_observation_reports.mjs`](../../tools/build_video_observation_reports.mjs)
строит операторский Excel-отчёт по стандартизированным наблюдениям и снимку
реестра автомобилей. В отчёте одна строка соответствует одному
нормализованному номеру, а не одному появлению в кадре. Основные вкладки:

- `Все номера` — частота всех наблюдаемых номеров по убыванию;
- `Ночные наблюдения` — та же картина, отсортированная по числу ночных
  появлений;
- `Найдено в БД` — точные совпадения с реестром, с квартирой и ФИО;
- `Не найдено в БД` — номера без точного совпадения, в порядке убывания
  частоты для последующей проверки охраной или оператором.

Поле `Ночь / День` показывает два независимых счётчика, например `18 / 14`.
Марка берётся как наиболее частая распознанная модель; при ничьей или её
отсутствии используется марка реестра, если номер найден точно.

## Комментарии и сопровождение кода

У трёх модулей есть верхние docstring-описания назначения. В стандартизаторе
и импортере также оставлены комментарии у границ ответственности: исходные
книги читаются только для чтения, а кэш БД не является реестром автомобилей.
В построителе Excel прокомментированы назначение листов и контрольные поля.
Этот документ является полной пользовательской справкой; комментарии в коде
объясняют локальную логику, а не заменяют её.

## Ограничения

- Видео показывает факт появления номера в кадре, но само по себе не
  подтверждает квартиру, владельца или право парковки.
- Близкие номера в операторской форме — лишь кандидаты для проверки,
  включая возможную ошибку OCR; они не являются совпадениями.
- Новые файлы следует добавлять в исходный каталог, затем запускать importer
  с `--apply`. Старые строки в кэше заменяются новым агрегированным снимком,
  а не копятся; история каждого обновления остаётся в журнале импорта и
  аудите.
