## 2026-07-19 — Finance Core architectural decision

A cashier case with a 700 UAH receipt (500 UAH known purpose and 200 UAH
unknown purpose) exposed a structural limitation: the system should not require
all received money to be classified by service immediately.

Decision: create the `finance_core` domain. Receipt/expense facts are recorded
first; allocations, reallocations, advances, refunds, and corrections are
recorded separately with a complete audit trail.

Created architecture documents:

- `Docs/Architecture/Finance_Core.md`
- `Docs/Architecture/ADR/ADR-2026-07-19-Finance-Core.md`

**Период:** 4 дня, 21-25 июль 2026
**Назначение:** хронология того, что сделано за это время — перенос проекта в `OSBB_cl` и доводка кассы. Формируется из рабочей переписки, не является итоговой архитектурной документацией (для неё см. `Docs/Architecture/`).

## 1. Перенос OSBB → OSBB_cl

### 1.1 Чистка старого OSBB
- Многократный триаж корня старого `OSBB` (`osbb_cleanup_triage.py`) — архивировано 600+ файлов: бэкапы, патч-бандлы, sandbox-раннеры, дубликаты.
- `dedupe_shadowed_functions.py` — найдено и устранено 36 дублирующихся функций в `db_access.py` (~1891 мёртвых строк). Оригинал в `Bots/db_access.py` не тронут (дедупликатор создаёт отдельную копию).

### 1.2 Архитектурное решение: зеркальная структура
- Первый подход (реорганизация в `presentation/`, `business_core/` и т.п.) — **отменён**: риск массово поломать импорты (`Bots.db_access`, `handlers.X` и т.д.).
- Принято окончательное решение: `OSBB_cl` **зеркалирует** структуру старого `OSBB` (`Bots/`, `tools/`, `core_new/`, `Data/`, `Docs/`) — реорганизация по подсистемам отложена до рабочей базовой версии.

### 1.3 Инструменты миграции (`OSBB_util/Scripts/`)
- `init_osbb_cl_skeleton.py` — создание каркаса (git, `main`, структура папок).
- `migrate_to_osbb_cl.py` — зеркальное копирование (482 файла), без разметки по подсистемам.
- `check_imports.py` — статический AST-аудит импортов. Несколько раундов исправлений false positive:
  - расширен список `KNOWN_EXTERNAL` (пропущены stdlib/сторонние: `telethon`, `warnings`, `glob`, `types`, `zipfile` и др.);
  - добавлено сопоставление по **суффиксам** пути (учёт паттерна "своя папка добавляется в `sys.path`");
  - исправлен расчёт относительных импортов (`from ..package import` — учёт уровня точек);
  - добавлено распознавание "голых" namespace-пакетов (`import handlers` без подмодуля).
  - Итог: со 107 неразрешённых записей до 0 реальных проблем (кроме объяснённых: `telegram_osbb` — секреты вне репозитория, один осиротевший `CHECK_*`-скрипт).

### 1.4 config.py
- Написан с нуля под `OSBB_cl`, кросс-платформенный (`Windows`/`Mac`).
- Добавлена совместимость со старым интерфейсом:
  - `USE_TEST_DB`, `OSBB_TEST_DB_FILE`, `OSBB_DB_FILE` — алиасы на единый `paths.DB_FILE`;
  - позже — **полный список всех 17 атрибутов** старого `config.py` (`OSBB_ROOT`, `OSBB_DATA_DIR`, `OSBB_QUARANTINE_DB_FILE` и т.д.), добавлены разом после повторных крашей по одному атрибуту.
- Решение об имени файла БД: **не переименовывать** `osbb_test.db` → `osbb.db` (было one отменено после того, как вызвало путаницу и один реальный баг — SQLite тихо создавал пустую БД при несовпадении имени).

### 1.5 Первый живой запуск
- Подтверждён живой запуск бота в `OSBB_cl` — тестирование через реальный Telegram (выбор языка, админ-режим, список авто, кассир).
- Найдена и устранена путаница из-за **параллельно запущенных двух процессов Python** (старый + новый) — оба слушали Telegram одновременно, объясняло множество "случайных" сбоев.
- `Start_OSBB_cl_Bot.bat` переписан: свой `.venv`, время старта и идентификация видны в заголовке окна консоли.
- `requirements.txt` урезан с ~150 личных пакетов до реально нужных проекту (`python-telegram-bot`, `Telethon`, `openpyxl`, `python-docx`, `reportlab`, `requests`, `python-dotenv`, `python-dateutil`, `pytz`, `tzdata`).

## 3. Касса — основная линия работы

### 3.1 Экран тарифов в боте
- Найдено расхождение: `service_items.amount_default` (откуда касса брала сумму) — пусто (`NULL`) везде; реальные тарифы лежат в отдельной, ранее не связанной таблице `service_tariffs`.
- `cashier_v2_core.py`: добавлена `get_current_tariff_amount()` — резервный источник суммы из `service_tariffs`, `service_items` остаётся приоритетным (если когда-нибудь заполнят).
- Новый экран `💵 Тарифы` в `ADMIN_MENU` — просмотр и изменение действующих тарифов (`Bots/handlers/tariff_editor.py`), с полноценным состоянием диалога и корректным `"Назад"`.

### 3.2 Хирургическое удаление платежей
- Реконструирована документация подсистемы (`Surgical_Delete.md`) по реальному коду `cashier_admin_ui.py`.
- Найден подтверждённый кодом пробел: `apply_cleanup_batch()` не пересчитывал `cashboxes.current_balance` после удаления.
- Патч: пересчёт баланса через уже существующий `cashier_operator.recalc_and_store_cashbox_balance()` — тот же механизм, что при обычной регистрации платежа.
- Проверено вживую на тестовом платеже (1 грн): баланс до/после сошёлся, независимо подтверждено прямым SQL-пересчётом.

### 3.3 Поиск платежей
- Найден и объяснён баг широкого текстового поиска (`search_payments_human`): короткие числовые запросы (`"1"`) тонули среди десятков нерелевантных совпадений (шумные поля `operator_id`, `period_code` и т.п.).
- Промежуточный патч (приоритет точной суммы в сортировке) — заменён на **полноценный экран с кнопками-фильтрами** (`🏠 Квартира`, `🏢 Фирма`, `🚗 Авто`, `👤 ФИО`, `💰 Сумма`, `📅 Дата`, `🧾 Номер чека`, `🔧 Код услуги`) — каждый со своей, подходящей логикой сравнения (точное/по фрагменту).
- Попутно найден и исправлен независимый баг: SQLite `LIKE` регистронезависим только для латиницы, не для кириллицы — затрагивало и ФИО, и фирмы; исправлено сравнением на стороне Python.
- Добавлен фильтр `🏢 Фирма` (поиск по `commercial_contracts.counterparty_name` через `unit_id → apartments`).
- Исправлен `IndexError`-крэш (`receipt_number` отсутствовал в выборке некоторых веток поиска).
- Добавлена защита `isinstance(state, dict)` — от чужого формата состояния между модулями (`tariff_editor` vs `cashier_admin_ui`).
- Частично улучшена навигация "Назад" (для поиска и карточки — из части экранов); **один случай (карточка платежа) остаётся нерешённым, записан как техдолг.**

### 3.4 "Последние чеки" (касса, `cashier_v2_ui.py`)
- Добавлен номер авто в вывод (был только длинный номер чека, бесполезный кассиру).
- Построен и протестирован **решатель "пазла"**: сумма платежа сверяется с тарифами известных авто квартиры (включая оплату за несколько месяцев сразу, `сумма = тариф × N`), убирает лишние "?" там, где сумма реально сходится, оставляет только для настоящей неопределённости.
- Найден и исправлен баг: авто без заданного `parking_time` пряталось за прочерком, будто его нет вовсе — теперь номер показывается всегда (с "?" при невозможности проверить сумму).
- Исправлен баг соединения (`vehicles.apartment_id`, не `apartment_number` напрямую).
- Таблица оформлена моноширинным блоком (`parse_mode='Markdown'`) — иначе Telegram рисует пропорциональным шрифтом, и колонки "плывут".
- Добавлена кнопка `🚗 Авто квартиры` — быстрый просмотр авто по номеру квартиры прямо из кассы, без выхода в `query_lib`/VS Code.

### 3.5 Журнал согласования (`verification_journal`)
- Спроектирована и протестирована таблица + функции (`log_verification_task`, `list_open_verification_tasks`, `resolve_verification_task`).
- В карточку платежа (`cashier_v2_ui.py`) добавлена кнопка `❗ На проверку` — **двухшаговый** диалог (выбор типа проблемы из классификатора → короткое уточнение одной фразой), не теряющий прогресс ввода платежа.
- Исправлен крэш (`apartment` в форме словаря, а не строки, в одном из сценариев выбора авто).
- Проверено вживую на реальном случае (кв.31, недостающее 3-е авто).

## 4. Находки и решения "по ходу", не привязанные к одному экрану

- **Разгадана путаница с несколькими процессами бота** (см. 1.5) — объяснила сразу несколько "необъяснимых" симптомов за день до этого.
- **Кодировка батника** — кириллица в `.bat`-файле рисовалась крякозябрами (несовпадение кодовой страницы консоли); решено заменой на английский текст в этой строке, не борьбой с `chcp`.
- **Уточнение по `#include` vs `import`** — не относится к делу проекта напрямую, но был содержательный разговор о том, почему модульная система Python избавляет от классических проблем C-препроцессора.
- Найден действующий, проверенный прецедент такого же паттерна "черновик → решение админа → применение" в `profile_verification_core.py` (`resident_profile_change_requests`, `resolve_profile_request`) — не про платежи, про полноту профиля жителя, но структурно то же самое, что мы строим для кассы.
