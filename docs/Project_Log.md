## 2026-07-19 — Finance Core architectural decision

A cashier case with a 700 UAH receipt (500 UAH known purpose and 200 UAH
unknown purpose) exposed a structural limitation: the system should not require
all received money to be classified by service immediately.

Decision: create the `finance_core` domain. Receipt/expense facts are recorded
first; allocations, reallocations, advances, refunds, and corrections are
recorded separately with a complete audit trail.

Created architecture documents:

- `Docs/Architecture/Finance_Core.md`

## 1. Перенос OSBB → OSBB_cl

### 1.1 Чистка старого OSBB
- Многократный триаж корня старого `OSBB` (`osbb_cleanup_triage.py`) — архивировано 600+ файлов: бэкапы, патч-бандлы, sandbox-раннеры, дубликаты.
- `dedupe_shadowed_functions.py` — найдено и устранено 36 дублирующихся функций в `db_access.py` (~1891 мёртвых строк). Оригинал в `Bots/db_access.py` не тронут (дедупликатор создаёт отдельную копию).

### 1.2 Архитектурное решение: зеркальная структура
- Первый подход (реорганизация в `presentation/`, `business_core/` и т.п.) — **отменён**: риск массово поломать импорты (`Bots.db_access`, `handlers.X` и т.д.).
- Принято окончательное решение: `OSBB_cl` **зеркалирует** структуру старого `OSBB` (`Bots/`, `tools/`, `core_new/`, `Data/`, `Docs/`) — реорганизация по подсистемам отложена до рабочей базовой версии.

### 1.3 Инструменты миграции (`OSBB_util/Scripts/`)
- `init_osbb_cl_skeleton.py` — создание каркаса (git, `main`, структура папок).
- `migrate_to_osbb_cl.py` — зеркальное копирование (482 файла), без разметки по подсистемам.
- `check_imports.py` — статический AST-аудит импортов. Несколько раундов исправлений false positive:
  - расширен список `KNOWN_EXTERNAL` (пропущены stdlib/сторонние: `telethon`, `warnings`, `glob`, `types`, `zipfile` и др.);
  - добавлено сопоставление по **суффиксам** пути (учёт паттерна "своя папка добавляется в `sys.path`");
  - исправлен расчёт относительных импортов (`from ..package import` — учёт уровня точек);
  - добавлено распознавание "голых" namespace-пакетов (`import handlers` без подмодуля).
  - Итог: со 107 неразрешённых записей до 0 реальных проблем (кроме объяснённых: `telegram_osbb` — секреты вне репозитория, один осиротевший `CHECK_*`-скрипт).

### 1.4 config.py
- Написан с нуля под `OSBB_cl`, кросс-платформенный (`Windows`/`Mac`).
- Добавлена совместимость со старым интерфейсом:
  - `USE_TEST_DB`, `OSBB_TEST_DB_FILE`, `OSBB_DB_FILE` — алиасы на единый `paths.DB_FILE`;
  - позже — **полный список всех 17 атрибутов** старого `config.py` (`OSBB_ROOT`, `OSBB_DATA_DIR`, `OSBB_QUARANTINE_DB_FILE` и т.д.), добавлены разом после повторных крашей по одному атрибуту.
- Решение об имени файла БД: **не переименовывать** `osbb_test.db` → `osbb.db` (было one отменено после того, как вызвало путаницу и один реальный баг — SQLite тихо создавал пустую БД при несовпадении имени).

### 1.5 Первый живой запуск
- Подтверждён живой запуск бота в `OSBB_cl` — тестирование через реальный Telegram (выбор языка, админ-режим, список авто, кассир).

- Найден действующий, проверенный прецедент такого же паттерна "черновик → решение админа → применение" в `profile_verification_core.py` (`resident_profile_change_requests`, `resolve_profile_request`) — не про платежи, про полноту профиля жителя, но структурно то же самое, что мы строим для кассы.

## 8. "Умное" разнесение платежа — распространено на историю платежей

## 9. Найден и исправлен серьёзный баг с периодами оплаты

- Диагностирован через цепочку: `payment_card()` → `draft_from_payer()` → `proposed_defaults()` (в `cashier_search.py`) → `latest_paid_period()` + `core.suggested_charge()` → `open_charges()` (в `cashier_v2_core.py`).
- **Причина:** все три функции считали "последний оплаченный период"/"следующее начисление" **по квартире и услуге**, без учёта `vehicle_id` — хотя колонка существует и полностью заполнена в данных (проверено: 0 пустых из 34+61 парковочных начислений). У квартир с 2+ авто одного режима (Day/Day или Night/Night) оплата одной машины сдвигала подсказку периода вперёд для другой, которая не платила вовсе.
- **Исправлено** добавлением параметра `vehicle_id` во все четыре функции (`open_charges`, `suggested_charge` — `cashier_v2_core.py`; `latest_paid_period`, `proposed_defaults` — `cashier_search.py`).
- Собран диагностический скрипт `find_suspect_vehicles.py` — находит квартиры с 2+ авто одного режима и считает реальные платежи по каждой машине; асимметрия (0 платежей рядом с "богатой" соседкой) — вероятная жертва бага, требует ручной сверки, не автокоррекции.
- Собран `fix_payment_period.py` — точечная правка `period_code` одного платежа, синхронно в `payments` и связанной `cashbox_operations` (связь подтверждена: `payments.cashbox_operation_id` ↔ `cashbox_operations.id`).
