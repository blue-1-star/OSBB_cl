## 2026-07-19 — Finance Core architectural decision

A cashier case with a 700 UAH receipt (500 UAH known purpose and 200 UAH
unknown purpose) exposed a structural limitation: the system should not require
all received money to be classified by service immediately.

Decision: create the `finance_core` domain. Receipt/expense facts are recorded
first; allocations, reallocations, advances, refunds, and corrections are
recorded separately with a complete audit trail.

Created architecture documents:

- `Docs/Architecture/Finance_Core.md`

## 1. Перенос OSBB → OSBB_cl

### 1.1 Чистка старого OSBB
- Многократный триаж корня старого `OSBB` (`osbb_cleanup_triage.py`) — архивировано 600+ файлов: бэкапы, патч-бандлы, sandbox-раннеры, дубликаты.
- `dedupe_shadowed_functions.py` — найдено и устранено 36 дублирующихся функций в `db_access.py` (~1891 мёртвых строк). Оригинал в `Bots/db_access.py` не тронут (дедупликатор создаёт отдельную копию).

### 1.2 Архитектурное решение: зеркальная структура
- Первый подход (реорганизация в `presentation/`, `business_core/` и т.п.) — **отменён**: риск массово поломать импорты (`Bots.db_access`, `handlers.X` и т.д.).
- Принято окончательное решение: `OSBB_cl` **зеркалирует** структуру старого `OSBB` (`Bots/`, `tools/`, `core_new/`, `Data/`, `Docs/`) — реорганизация по подсистемам отложена до рабочей базовой версии.

### 1.3 Инструменты миграции (`OSBB_util/Scripts/`)
- `init_osbb_cl_skeleton.py` — создание каркаса (git, `main`, структура папок).
- `migrate_to_osbb_cl.py` — зеркальное копирование (482 файла), без разметки по подсистемам.
- `check_imports.py` — статический AST-аудит импортов. Несколько раундов исправлений false positive:
  - расширен список `KNOWN_EXTERNAL` (пропущены stdlib/сторонние: `telethon`, `warnings`, `glob`, `types`, `zipfile` и др.);
  - добавлено сопоставление по **суффиксам** пути (учёт паттерна "своя папка добавляется в `sys.path`");
  - исправлен расчёт относительных импортов (`from ..package import` — учёт уровня точек);
  - добавлено распознавание "голых" namespace-пакетов (`import handlers` без подмодуля).
  - Итог: со 107 неразрешённых записей до 0 реальных проблем (кроме объяснённых: `telegram_osbb` — секреты вне репозитория, один осиротевший `CHECK_*`-скрипт).

### 1.4 config.py
- Написан с нуля под `OSBB_cl`, кросс-платформенный (`Windows`/`Mac`).
- Добавлена совместимость со старым интерфейсом:
  - `USE_TEST_DB`, `OSBB_TEST_DB_FILE`, `OSBB_DB_FILE` — алиасы на единый `paths.DB_FILE`;
  - позже — **полный список всех 17 атрибутов** старого `config.py` (`OSBB_ROOT`, `OSBB_DATA_DIR`, `OSBB_QUARANTINE_DB_FILE` и т.д.), добавлены разом после повторных крашей по одному атрибуту.
- Решение об имени файла БД: **не переименовывать** `osbb_test.db` → `osbb.db` (было one отменено после того, как вызвало путаницу и один реальный баг — SQLite тихо создавал пустую БД при несовпадении имени).

### 1.5 Первый живой запуск
- Подтверждён живой запуск бота в `OSBB_cl` — тестирование через реальный Telegram (выбор языка, админ-режим, список авто, кассир).
- Найдена и устранена путаница из-за **параллельно запущенных двух процессов Python** (старый + новый) — оба слушали Telegram одновременно, объясняло множество "случайных" сбоев.
- `Start_OSBB_cl_Bot.bat` переписан: свой `.venv`, время старта и идентификация видны в заголовке окна консоли.
- `requirements.txt` урезан с ~150 личных пакетов до реально нужных проекту (`python-telegram-bot`, `Telethon`, `openpyxl`, `python-docx`, `reportlab`, `requests`, `python-dotenv`, `python-dateutil`, `pytz`, `tzdata`).

- Собран `apply_state_guard.py` — автоматически находит все места вида `state = user_states.get(user_id...)` и добавляет защиту `isinstance(state, dict)`, если её ещё нет; идемпотентен, делает `.bak`-копию перед правкой. Применён разом к пяти файлам (`agreement.py` — 3 места, `tariff_editor.py`, `cashier_ui.py`, `user_onboarding/admin_ui.py`) — семь защит добавлено одним заходом.
- Заодно собран `check_syntax.py` — безопасная проверка синтаксиса нескольких файлов разом, без ловушки экранирования обратного слэша в путях Windows при использовании `python -c` (то, на чём споткнулись при проверке вручную).

## 20. Защита от ошибочного «добавления» вместо исправления автомобиля

- В свободном сценарии «добавить автомобиль» бот теперь извлекает введённый госномер и сравнивает его с уже известными жителю автомобилями той же квартиры.
- При полном совпадении или отличии в один символ бот показывает понятный выбор: оформить исправление существующего авто либо явно подтвердить, что это всё же другой автомобиль. Заявка на добавление не создаётся молча.
- При выборе исправления создаётся структурированная заявка `RESIDENT_VEHICLE_UPDATE`, привязанная к конкретному `vehicle_id`; реестр автомобиля до решения оператора не меняется.
- Значение, введённое жителем, является только версией для проверки. В операторской карточке оно показывается отдельно от текущего номера; поле «Проверенный госномер» намеренно пустое и заполняется оператором по надёжному источнику перед сохранением.

## 30. Рекомендация при заявке жителя на добавление автомобиля

- Операторский редактор сначала пропускает номер из заявления через общий
  нормализатор номера; из свободного текста также извлекается отдельный
  фрагмент формата `AA1234BB`.
- Зелёная рекомендация не создаёт автомобиль сама. Она доступна только для
  нового стандартного номера с независимым подтверждением: видео со статусом
  `CONSENSUS` или записью того же номера для той же квартиры в историческом
  импорте старого бота. Оператор применяет подготовленные значения одной
  кнопкой подтверждения.
- Жёлтая рекомендация подставляет очищенные поля, но требует отдельного
  подтверждения после проверки. Точное совпадение с `vehicles` — красный
  стоп-сигнал: форма блокирует создание дубля. Уровень рекомендации и
  использованные источники сохраняются в аудите создания автомобиля.

## 31. Структурированное удаление ошибочно внесённого автомобиля

- В кабинете жителя добавлена отдельная кнопка «Автомобиль внесён ошибочно»;
  она создаёт заявку `RESIDENT_VEHICLE_REMOVE` и никогда не меняет реестр
  напрямую. Свободное «другое изменение» больше не показано в обычном меню;
  старые заявки остаются доступны оператору для ручного переопределения.
- Экран оператора показывает явный второй шаг после взятия заявки в работу и
  проверяет все связанные с автомобилем финансовые и рабочие записи. При
  отсутствии связей доступно подтверждённое физическое удаление; при их
  наличии — только архивирование с сохранением истории.
- Для старой текстовой заявки предусмотрено действие «Переопределить как
  автомобиль внесён ошибочно»: исходный текст сохраняется, смена типа
  фиксируется в `audit_log`. Удаление/архивирование и закрытие заявки также
  происходят в одной аудируемой транзакции.

## 32. Продажа автомобиля: финансовый блокер до подневного расчёта

- Миграция `2026-09-21_015_add_vehicle_parking_end_fields.py` добавила в
  `vehicles` дату, причину и финансовый статус прекращения парковки. Резервная
  копия создана до изменения; миграция не архивировала автомобили и не меняла
  начисления или оплаты.
- Для `RESIDENT_VEHICLE_PARKING_END` пустой режим `Day`/`Night` проверяется
  уже в кабинете жителя. Если в истории оплат квартиры нет однозначного
  признака режима, сначала направляется отдельное предложение указать режим.
  Если все связанные оплаты помечены одним режимом, бот и оператор показывают
  жёлтую рекомендацию, которую оператор подтверждает отдельным действием.
- Экран заявки показывает прямые связи авто и все оплаты/начисления квартиры.
  Оплата квартиры без `vehicle_id` не распределяется предположением. При
  неизвестном режиме без доказательств заявка переводится в
  `NEEDS_CLARIFICATION`; финансово завершить продажу можно только после
  подтверждённого режима и отдельной подневной корректировки, если обнаружены
  финансовые записи.
- Реализована операторская корректировка: для месяца даты прекращения система
  показывает тариф, число оплачиваемых дней и подходящие оплаты той же
  квартиры, периода и режима. После явного подтверждения создаются частичное
  начисление и `payment_allocation`; остаток квартирной оплаты сохраняется
  нераспределённым. Архив автомобиля и закрытие заявки происходят в той же
  аудируемой транзакции.
- Если финансам не хватает достоверности (нет оплаты нужного периода, режим
  неизвестен или исторические строки требуют сверки), продажа больше не
  блокируется. Оператор архивирует авто с датой, подтверждённой жителем, а
  система создаёт отдельную внутреннюю задачу
  `PARKING_END_FINANCIAL_RECONCILIATION`; начисления и оплаты в этом пути не
  меняются.
- Кабинет жителя разделил обращения на `📨 Ожидающие` и `🗂️ История`:
  технические дубли и уже решённые заявления не мешают видеть текущие задачи.
  В Streamlit-очереди добавлены соответствующие фильтры `Ожидающие` и
  `Обработанные`.
- Миграция `2026-09-21_016_add_resident_request_messages.py` добавила
  аудируемую переписку по self-service заявкам. Операторский вопрос ставит
  заявку в `NEEDS_CLARIFICATION`, бот доставляет его из очереди, а ответ
  жителя сохраняется в той же ветке и возвращает заявку в `PENDING`.
- Миграция `2026-09-21_017_add_resident_resolution_notifications.py` добавила
  автоматическое итоговое уведомление: при `RESOLVED`, `REJECTED` или `CLOSED`
  для заявки из кабинета жителя триггер создаёт Telegram-сообщение с номером
  заявки и итоговым комментарием. Очередь доставки отдельно различает вопрос
  оператора и окончательный результат; оба события аудируются.

## 35. RBAC: глобальная роль супер-администратора

- Миграция `2026-09-22_020_register_super_admin_rbac.py` создаёт/активирует
  настоящую роль `SUPER_ADMIN` и переносит в неё активные записи
  `bot_admins.role='super_admin'`.
- Проверка прав в основном `access_control.py` распознаёт только активное
  назначение этой RBAC-роли, а не секретный Telegram ID. `SUPER_ADMIN`
  преднамеренно имеет глобальный доступ для восстановления ошибочной
  конфигурации ролей; каждое назначение фиксируется в `access_audit_log`.

## 36. Уточнение маршрута физического товара

- Для пультов и других физических предметов путь выдачи определяется
  фактическими передачами каждой единицы: ЦС → консьерж → житель,
  ЦС → житель либо ЦС → представитель группы → жители указанных квартир.
  Одну поставку можно разделить между несколькими маршрутами.
- Приём представителем подтверждает его ответственность за полученную часть
  партии, но не подтверждает получение жильцами. Квартирное назначение и
  конечное получение должны фиксироваться отдельно.
- `REMOTE_NEW_PREORDER` остаётся техническим профилем предыдущего тестового
  сценария. Его прямой шаг выдачи не следует считать утверждённым маршрутом
  нового товара; детали приведены в архитектурном документе.
